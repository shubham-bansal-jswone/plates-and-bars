# Plate & Bar — Prototype Behaviour Spec

**Status:** source of truth for app behaviour. The HTML prototype is frozen at git tag `prototype-final` and removed from the tree; this document and `docs/spec/golden/` are the spec of record. Change them only in a `spec-change` PR (see `docs/AGENTS.md`).
**Golden fixtures:** `docs/spec/golden/*.json`, originally generated from the prototype and no longer regenerated. Ported code must reproduce them exactly.

Citations below to the prototype name a function in the `prototype-final` tag (`docs/prototype/plate-and-bar.html` at that tag, frozen at tag `prototype-final` and since removed from the tree). Order of authority when they disagree: `docs/spec/golden/` fixtures first, then this document's prose, then the frozen original at tag `prototype-final` (historical reference only). File an issue so the lower source is brought in line.

## 0. Changes since the Development Plan was written

**2026-10-29 — milestones derived from stored data (#1351 C6; addition, no prototype counterpart).** New: `packages/core/src/milestones.ts`, vectors in `docs/spec/golden/milestones.json`. `milestones(sets, sessions, weights, types, unit, end, profile?)` returns the earned milestones with the date first earned, newest first (same date by `id`), each `{ id, kind, title, detail, date }`. Derived on every call and never stored, so a milestone stays while its data exists and goes away if the set or session is deleted. No points, levels, streaks or locked entries; badges are #1356. Only data on or before `end` counts. (1) Plates: first done work set (not fail, not deleted, at least 1 rep) of a `barbell`-typed lift (from `types`, built through `exInfo`; a missing name is not barbell) at 60/100/140 kg (a 20 kg bar with 20 kg plates; the same steps in every unit, so switching kg and lb never moves or removes a milestone and the unit only changes the wording; an lb user earns "One plate a side" at about 132 lb, so the wording must not imply 45 lb plates). The steps use a float epsilon only (59.9 kg is not a plate); there is no lb clause, as every lb step is heavier than its kg step. The detail shows the lightest set of the first qualifying day (the one that crossed the step). Barbell-typed EZ-bar lifts (`EZ_BAR_LIFTS`: Preacher Curl) do not count. Titles are words (One/Two/Three plates a side). (2) Bench at bodyweight and (3) squat at 1.5 x bodyweight: first such set of a named library lift (`BENCH_LIFTS` = Barbell Bench Press, `SQUAT_LIFTS` = Barbell Back Squat) at or above the bodyweight of that day (`latestWeight` on or before it, else the profile weight; none known, no milestone; float epsilon only, so 79.9 kg at 80 kg is not earned; the heaviest set of the day is shown). (4) 10th, 50th and 100th workout: days with at least one logged set in the session log, the `sessionDates` rule. (5) First 4 consecutive on-track weeks, scanned Monday by Monday with `habits` (`weeks >= 4`), dated the Sunday before that Monday; profile `days: 0` has no plan. (6) New best estimated 1RM is not a milestone: it is the Recent PRs list (`personalRecords`, C3). The app (A9) decides "newly earned" from a stored set of shown ids, not from `date === today` (the plan block is dated the day before it first appears). The final `profile` argument is an addition to the issue's signature, needed for the profile weight and the plan goal.

**2026-10-29 — Weekly done sets per muscle and volume vs plan in core (#1351 C2; additions, prototype and existing golden fixtures unchanged).** New, not prototype ports: `packages/core/src/progressVolume.ts`, vectors in `docs/spec/golden/progressVolume.json`. `weeklyDoneSets(days, end, weeks, tags)` returns, oldest first, one row per Monday-week for the `weeks` weeks ending at the week containing `end` (the viewed date): `{ week (Monday), sets per muscle, partial }`. Mirrors `doneCoverage`: the per-day counting (done work sets, not ramp, not deleted, in a non-deleted workout, exercise in the workout's list, primary 1, secondary 0.5, untagged nothing) is now one function, `addDoneSets` in `coverage.ts`, used by both, so the last week equals `doneCoverage` on that week's Sunday (tests assert this on every fixture). Every `COVER_SHOW` muscle is present and a week with no sessions is 0, not null (a real zero of done sets). The week is the whole Monday-Sunday week by calendar days (DST-safe; days after `end` count when they hold data), and `partial` is true when `end` is not that Sunday; this is relative to the viewed date, so a past date mid-week shows that week in progress as of that day, even though it is over in real time. `volumeVsPlan(weeks, planned, since)` returns `{ basis: 'current-plan', weeksUsed, rows }`, a row per `COVER_SHOW` muscle: `avg` is the mean over the last 4 complete weeks (a `partial` week is skipped so a Tuesday does not read as under target; `since` is the user's first logged workout date: weeks ending before it are left out, so the empty weeks before the user started are not misses, and the week containing `since` counts as partial unless `since` is a Monday; `since` null (or an empty string) means no history, so `weeksUsed` is 0, averages 0 and nothing is below; fewer usable weeks are averaged as they are; example: first workout Monday 2026-10-12, 12 chest sets in each of the two weeks since, viewed 2026-10-29 with 12 weeks gives avg 12 and is not below a plan of 12), `target` is `plannedCoverage` of the CURRENT plan (never a past target; the app labels it so), `gap = avg - target`, `below = target > 0 and avg < target` (false with no usable week), and `low`/`barPct` keep `COVER_LOW` (6) and `COVER_FULL` (12) as the meter has them. Values are unrounded. The app slice formats them.

**2026-10-29 — weekly intake averages and weeks-on-track series in core (#1351 C4, C5; additions, prototype and existing golden fixtures unchanged).** New, not prototype ports: `weeklyIntake` and `weeksOnTrackSeries` in `packages/core/src/progressSeries.ts`, vectors in `docs/spec/golden/weeklyIntake.json` and `weeksOnTrack.json`.
- `weeklyIntake(days, end, weeks, targets)`: one row per Monday-week for the `weeks` weeks ending with the week that holds `end`, oldest first: `loggedDays`, `avgKcal`, `avgProtein_g` (unrounded), `partial`, and the current `targets` (`{ kcal, protein_g }`, the same on every week). A day is logged when it has at least one live (not deleted) food log, the rule `weekSummary` and `habits` use (the `complete` flag is not used, since a user who forgot to tick the day still ate). Averages are over logged days only; days after `end` are ignored, so the current week averages its days so far. A week with no logged day has null averages, never 0 kcal (as the #503 bar says "not logged"). 1 to 3 logged days (below `WEEKLY_INTAKE_MIN_DAYS` = 4) is `partial: true` with its values.
- `intakeAverage(weeks, lastN = 4)` (#1351 A6, added with the Eating by week card): the average kcal and protein per logged day over the last `lastN` rows of a `weeklyIntake` series, every week weighted by its logged days (a 2-day week counts for 2 days; not a mean of week means), weeks with no logged day skipped, `{ avgKcal, avgProtein_g, loggedDays }` with null averages and 0 days when none (never 0 kcal). Vectors: `intake_average` in `weeklyIntake.json`.
- `weeksOnTrackSeries(sessions, profile, end, weeks)`: the per-week form of `habits().weeks`: for each of the last `weeks` COMPLETED Monday-weeks (the week holding `end` is left out, as in `habits`), oldest first, `{ weekStart, sessions, goal, onTrack }`. The goal rule is extracted from `habits` and shared (`weeklySessionGoal`: plan days minus 1, minimum 2; `weekOnTrack`: at least goal session dates in the week), so `habits` output is unchanged. The trailing run of `onTrack` equals `habits().weeks` (which stops at 26); a test asserts it on fixtures and on generated histories.

**2026-10-30 — one exercise name per session (#1340, owner decision; closes #1329; addition, prototype and the plan and sessions fixtures unchanged).** New, not a prototype port: core `dedupeExercises` in `routines.ts`, vectors in `docs/spec/golden/dedupe.json`. Sets are stored by exercise name, so two entries of one name would share set rows after a reload; a session therefore never holds one name twice. `dedupeExercises(exs)`: the first occurrence keeps its place and fields; a later copy is dropped and its set count is added to the first, capped at the per-exercise set limit (`ROUTINE_SETS_MAX`, 20; a first copy already above it is not cut); then `normalizeGroups` repairs any group the removal broke (ADR 012). Applied at every source: the plan engine needs no change (the prototype's `resolveSession` drops repeats, #110 and #143, and `trimSession` and `applyFocus` work from distinct names; the golden plan and session fixtures are unchanged); `replaceAt` refuses a pick already in the session, the replaced exercise included, and changes nothing (the sheet never offers one, and the app does not save a rule or toast a swap for it); `startRoutine` runs the rule on a stored routine that repeats a name (it used to keep each copy with its own count; the one test that pinned that now expects one merged entry); a three-way sync merge and the union of two copies end with one entry per name; on load a stored session that repeats a name shows one entry holding all of that name's set rows (none is lost), and the cleaned list is written back by the next real edit, never silently on load. Workout import (`planImport`) already numbered sets per stored name in file order and so merged repeats, including two imported names mapped to one stored name; vectors pin that and keep a superset only while the merged exercises are still 2 to 6 adjacent members with one id (an exercise whose sets disagree stays ungrouped, #1338).

**2026-10-30 — weekly bar chart layout (#1351 A3; new rule, no prototype counterpart).**
- Prototype: the Seven-days bars of `renderProgress` are fixed-height CSS bars; there is no chart of weekly values over a range.
- New rule: core `barLayout(values, target, box)` lays out one bar per week value in the weight chart's box: one slot each from `px` to `W - 8`, a bar 70% of its slot and at most `BAR_MAX_WIDTH` (40 box units, about 70 px at the widest chart) wide, centred, rising from a zero baseline to the tallest value (1 when there is none) and at least `BAR_MIN_HEIGHT` (2 units) tall, so a real 0 shows a stub and differs from a gap. A null value is a gap: no bar (the #503 rule, "not logged", never 0). A finite target above 0 is drawn however far from the bars (the axis grows to include it, so short bars stay truthful); a target of 0 or less or not finite is ignored. A target changes heights but never x or width, as in `chartLayout`.
- The app's `BarChart` draws a partial week hollow and labels it "few days logged"; flags a week below the target (compared by the chart's number format, so a week that reads as the target is "On target") with an inner ring and the text "Below target" in the table (a partial week is not flagged); and speaks a count summary ("12 weeks from 14 Sept to 12 Oct. 5 below target, 2 with few days logged, 1 not logged").
- Core `packages/core/src/progress.ts`, vectors in `docs/spec/golden/bar-layout.json`. Shipped with the app slice in one PR under the lane waiver for #1354 (coordinator, 2026-10-30).

**2026-10-29 — personal bests use the all-time best, with a list and a tick-time check that agree (#1351 C3; spec change, new rule replacing the prototype's last-8 rule).**
- Prototype: `updateLift` computes `beforeBest` as the max over the lift record's `hist`, which keeps only the last 8 sessions, and `checkBest` toasts when today's score beats it by more than 0.5% (`1.005`) with at least 2 scores in `hist`. After a break this can call a non-record a personal best (it only beat the last 8 sessions).
- New rule: a personal record is a day whose score beats the best score of ALL earlier days by MORE than 0.5% (`PR_THRESHOLD`) with at least one earlier session (`PR_MIN_PRIOR_SESSIONS` = 1, `checkBest`'s "at least 2 scores" counting today; the owner note's "at least 2 prior sessions" is read as `checkBest`'s rule, coordinator 2026-10-29). The first session never counts; an equal value never repeats; the running best only rises, also on days that fail the 0.5% test. A day is a date (two workouts on one date are one day). The test is strict and float-safe: the two scores are compared as whole tenths (`round(cur*10)*1000 > round(best*10)*1005`), so exactly +0.5% (100.5 against 100) is NOT a record; the prototype's `cur > best * 1.005` lets it through by float error (`100 * 1.005 = 100.49999999999999`), a difference not kept.
- The score depends on the lift's type, and every type keeps a PR toast, with the toast and the list agreeing. Loaded lifts (`metric` 'e1rm') use the estimated 1RM of `e1rm.ts`: done work sets, not deleted, not rated fail, 1 to 12 reps, a single scores its weight, the best set of the day (ties to the heavier set). This is a deliberate difference from today's toast, which scores with uncapped Epley over every ticked set: (b) a fail-rated set no longer counts; (c) sets over 12 reps no longer count, and a day of only such sets is not a session; (d) a single scores its weight, not `w x 1.033` (prior 100x5 = 116.7, today 117x1: today's toast fires, the new rule does not). Bodyweight and timed lifts (`metric` 'reps') use total reps and assisted lifts (`metric` 'assisted') use the bodyweight-minus-assist score, both as `sessionScore` with the same counting as `updateLift` (done work sets with a weight or reps, a fail set still counts); `isPrToday` takes the bodyweight for assisted lifts the way `updateLift` gets it (latest logged weight, else the profile's). (e) Assisted lifts rescore every earlier day at the bodyweight passed in now, so a weight change alone neither makes nor hides a PR (today's `hist` keeps each day's score at that day's bodyweight, and a weigh-in alone can toast); the app passes the same bodyweight to `priorBestOf` and `isPrToday` and drops its cached prior best on a new weigh-in. A best of 0 or below never counts as a best (floored at 0), so the first day scoring above 0 is not a PR either. The floor applies to assisted lifts (negative scores only occur with no bodyweight, which the app never passes) and to bodyweight lifts with days of weight-only, 0-rep sets. A done set with weight and reps both 0 is ignored, as in `updateLift`. The 0.5% rule and minimum history are the same for all types.
- Core `packages/core/src/records.ts`, vectors in `docs/spec/golden/records.json`: `personalRecords(sets, types, bodyweight?)` (the Recent PRs list: lift, date, metric, score, the set, previous best, delta, newest first), `isPrToday(prior, todaySets, type, bodyweight?)` (the tick-time check, returns what improved or null; same rule, so the toast and the list agree), `priorBestOf(sets, type, date, bodyweight?)` (all-time best and earlier-session count from stored sets) and `mainLifts(sets, types, end)` (top 3 loaded lifts by DAYS with an e1RM in the 12 weeks up to and including `end`, the viewed date (today when viewing today), at least 3 days, ties to the most recent day then name; bodyweight, timed and assisted excluded; as for records, two workouts on one date are one day). The app builds `types` with `exInfo(name, catalog, override).type` for every lift, overrides included; a name missing from `types` is read as loaded.
- Owner decision (2026-10-29): the app's PR toast moves to this rule, once per lift per day and untick behaviour unchanged, text "New personal best: Bench Press 100 kg x 5, estimated 1RM 116 kg (+3 kg)" in the user's unit (for bodyweight lifts by `metric`, e.g. "Pull-up: 32 reps in total (+3)"). `checkBest` and `updateLift` are unchanged in this PR; the app slice switches over (A4b). The prototype's last-8 rule stays in `stalls.ts` until then.

**2026-10-29 — Progress chart series rules in core (#1351 C1; additions, prototype and existing golden fixtures unchanged).** New, not prototype ports: `packages/core/src/progressSeries.ts` and `measureSeries` in `progress.ts`, vectors in `docs/spec/golden/progressSeries.json`. `rangeSeries(points, end, '4w' | '12w' | 'all')` keeps the points dated on or after `end` minus 28 days (4w) or 84 days (12w), the boundary day included; `end` is the series end date, the viewed date (today when viewing today), the same `upTo` the series were built with; 'all' keeps every point; order is kept. `downsampleWeekly(points, 'last' | 'max')` applies only to more than `DOWNSAMPLE_THRESHOLD` (120) points, otherwise the series is returned as a copy, unchanged; above it gives one point per Monday-week (`mondayOf`, calendar days so DST does not matter), oldest first: the week's latest point for 'last', its highest value for 'max' (earliest on a tie); the kept point keeps its own date. `measureSeries(tapes, key, date, limit = 20)` is `waistSeries` for any tape part (`waist_cm`, `neck_cm`, `chest_cm`, `arm_cm`, `thigh_cm`, `hips_cm`, the `content/measures.json` parts): nonzero values on or before `date`, deleted rows ignored, last `limit` points oldest first (`Infinity` keeps all; 0, a negative or NaN gives none); `weightSeries` takes the same `limit`, default `WEIGHT_CHART_POINTS` (30), so 12w and All are not cut to 30; `waistSeries` now calls it with `waist_cm` and its output is unchanged (tests pin the pre-change output for waist and weight as literals).

**2026-10-29 — saved routines: Save as routine, My routines, start (#1184, ADR 011; an app-only feature, prototype and golden fixtures unchanged).**
- The prototype has no saved workouts. The app lets the user save a session as a named routine (a list of exercises with set counts, from the Workout screen and from the completion panel), and start it later. Regenerating the app from the prototype must not remove it.
- Stored: name (1 to 60 characters counted as code points, not blank) and 1 to 50 exercises of `{ name, sets }`, sets 1 to 20, repeats and blank names dropped. Reps and weights are not stored; they come from progression when the routine is started. At most 100 live routines per account; the app refuses the 101st (Save as routine, and Undo of a delete) before it saves. A routine is a record of the `routines` sync table (17th table, random id, so two routines never conflict; `docs/adr/011-routines-sync-table.md`).
- Start screen: a "My routines" section beside the generated plan, shown only when at least one routine exists. Each row has the name, the exercise count, Start and Edit (rename, delete). Routines do not replace plan days and do not change the next-workout rotation: a routine session is stored as hand-picked ("Session", no base), which sequence mode skips.
- Start keeps each stored set count as saved (no 3 floor, no 5 cap, no beginner ramp, no focus or calf bump); only the recovery-week and lighter-session steps apply (core `startRoutine`), and no lab hold (as for hand-picked sessions, #1088). An exercise the library no longer has, or the user's rules exclude, stays in the session and is flagged with a Remove button (core `missingExercises`). The flag shows on every hand-picked session (Pick exercises as well as a routine start), not on planned ones. Start never overwrites a session already stored for the day.
- Delete is a tombstone with an inline Undo that brings back the same id; the Undo stays until used, until another delete, or until the routine is back (also while a preview or pick list hides the section). Delete and Undo are announced, and focus moves to the next row's Edit (or the section heading) after Delete and to the restored row's Edit after Undo.


**2026-10-29 — exercise groups (supersets) rules in core (#1182 S2, ADR 012; addition, prototype and golden fixtures unchanged).** New, not a prototype port: `packages/core/src/groups.ts`, vectors in `docs/spec/golden/groups.json`. A session exercise may carry a `group` id; members of a group are contiguous in `exercises[]`, a group has 2 to 6 members (`GROUP_MIN`, `GROUP_MAX`), null or absent is ungrouped; an id failing the contract pattern `^[A-Za-z0-9_-]{1,36}$` (empty, number, space, over 36 characters) is repaired to null. `normalizeGroups` repairs a bad list without reordering: an id in more than one run is dissolved, a run under 2 is dissolved, members past the sixth are ungrouped; changed exercises get an explicit `group: null`, others are returned as they were. Labels (A, B, C) come from the order within the group; a set is A1, B1, A2, B2. Sets alternate by round, and a member that runs out of sets drops out of later rounds; after the last round the next exercise follows. Rest (`restAfterTick`): the global rest-off setting disables all; `nextInRound` and `restAfterTick` are done-aware (they take the done state; the ticked set counts as done). Ungrouped they match the app's tick (`useWorkoutDay.ts`:451-455): next set is the first undone set of the exercise, else the first later exercise with an undone set (finished ones skipped), else nothing; when nothing undone is left from the exercise onward no rest starts (kind `none`, 0 seconds, next null); otherwise the rest is `restFor`. In a group the next set is the first undone in alternating order (A1, B1, A2, B2), then the first later exercise or group with an undone set, entering a group in round order (its first undone set among A1, B1, A2, B2, so with [x, A, B], A1 done and B1 open, ticking x goes to B1, and ticking B1 then goes to A2); a round is open while another member has an undone set at that round's index or earlier, so ticking B1 before A1 is a 15 second transition rest (`GROUP_TRANSITION_SEC`), and the tick that closes the round starts the longest `restFor` among the members still in that round. A set index past every member's sets gives kind `none`; a set index that exists on another member but not on the ticked exercise is treated as normal (round rules apply). A group id found in more than one run is ungrouped in order, rest and labels alike. The warm-up and ramp stay a per-exercise pre-step, outside the rounds. Progression, suggestions, e1RM and records stay per exercise name; `progression.ts` is unchanged. Timed circuits are deferred. The rest dock and screens are a later slice. Swap (#1331): core `replaceAt` copies the replaced exercise's `group` onto the pick at the exact index, so a can't-do swap keeps the group (ungrouped sessions unchanged); a ticked swap keeps the original ticked member in place, and in a full group of 6 the new exercise is the one left ungrouped, placed right after the group so it stays contiguous; a group left under 2 members is dissolved.

**2026-10-28 — features the app adds that the prototype does not have (additions; prototype and golden fixtures unchanged).** The prototype is kg only, has no plate calculator, no share image and no restore. Regenerating the app from the prototype must not remove these, and they are not drift. Only merged parts are described; open work is marked in progress.
- **Weight unit kg or lb (#1185).** Core merged in PR #1257 (`packages/core/src/weightUnit.ts`, with `kgLabel`, `infoForUnit` and `snapForUnit` in `progression.ts`); the app setting and the workout session screens merged in PR #1279; Progress, History, Setup and Targets are in progress (PRs #1289, #1292). The unit is a device-local setting, never synced, kg by default. Storage, the contract and every calculation stay in kg (`weight_kg` unchanged); conversion happens only where weights are shown or typed (`KG_PER_LB = 0.45359237`, one decimal). lb users get an lb step grid (`LB_STEP`: barbell 5, dumbbell 2.5, machine/cable/assisted 5, other 2.5). On holds, light days, deload days and re-entry days the lb rounding goes toward easier (down for loaded types, more assistance for assisted), never heavier than last time. In kg the output is identical to the prototype.
- **Estimated 1RM and elapsed session time (#1178).** Core merged in PR #1267 (`packages/core/src/e1rm.ts`); the app screens merged in PR #1276 (History e1RM trend, session time on the completion panel and the History day view). Epley `w x (1 + r/30)` (the prototype uses it only inside `sessionScore`), one rep is the weight itself, reps above `E1RM_MAX_REPS` (12) give no estimate. Only done work sets not rated fail count, and not bodyweight, timed or assisted exercises. The trend keeps the best estimate per session. Elapsed time is first to last done-set tick minus any gap over 3 hours (`SESSION_GAP_MS`); a duration is shown only when every done set has a usable tick (ticked warm-up sets count) and there are at least two; when a long gap is cut it reads "about ... of training (long break excluded)".
- **Plate calculator (#1176).** Core merged in PR #1277 (`packages/core/src/plates.ts`, `platesFor`); the app sheet merged in PR #1290 (opened from barbell set rows and from the exercise detail in the Library). Gives the plates per side for a target bar weight. Defaults: 20 kg bar with 25, 20, 15, 10, 5, 2.5, 1.25 kg plates, or 45 lb bar with 45, 35, 25, 10, 5, 2.5 lb plates. By default an unreachable target loads the nearest weight at or below it and reports the remainder; a target under the bar returns the bar alone.
- **Shareable workout summary image (#1180).** Merged in PR #1270. The workout completion panel has a secondary Share action that draws a fixed dark summary card on the device (1080x1350 PNG; `react-native-view-shot` on Android and iOS, a canvas download on web) and opens the system share sheet on Android and iOS; on web the PNG downloads and no share sheet opens. Nothing is uploaded. The card (`buildShareCard`) shows only the day, sets, volume in the user's unit (or reps), exercise count, cardio minutes, each exercise's best set and personal records; never body weight, calories, how a set felt, health answers or identifiers. More than 7 exercises end in "+N more". The session time is not on the card. A share from the History day view is planned (#1278).
- **Restore from a local export file (#1177).** Merged in PR #1273. The Data screen can restore a device export file: strict validation (size cap before reading, format version 1 and device source only, known tables, row and depth caps), a per-table summary, and nothing written until the user confirms. It merges, never replaces: a higher record version wins, an equal version falls to the later `updated_at`, tombstones delete, and a local row with an unpushed edit is kept. One transaction, through the table triggers, so restored rows sync like any edit. The cycle log is added only where the device has none; lab reports the device lacks are added by date and id even when other reports exist (a restore can turn the lab hold on, never off); consents are never restored. A file from a different account only adds rows the device lacks and keeps existing rows whatever their version, and the preview flags it. A restored kitchen-test tombstone also deletes that test's local photo. Photos are not in the file.

**2026-10-28 — lab reports: "Summary for my doctor" and no lab hold on hand-picked sessions (#1088; deliberate differences, prototype and golden fixtures unchanged).** (1) The app builds a plain-text "Summary for my doctor" of the saved lab reports: each report's date, its tests with value, unit, the lab range as entered and the app's flag word (and "unit not recognised" where the results card says so), then the informational disclaimer from `content/labs.json`. **2026-10-28 — graduated warm-up ramp and warm-ups on later compounds (deliberate differences; prototype and golden fixtures unchanged).**
- #1240 (decision), #1241 (core, PR #1246), #1242 (app). The prototype's `warmupHtml` (prototype-final tag, `warmupHtml`) stays the spec below 60 kg on the first loaded, non-assisted compound: "Warm up first: 8 reps at 50%, then 4 at 75%. Not logged.", weights snapped to the exercise step. `warmupSets` stays the prototype port.
- Deliberate differences, from `warmupRamp` in `packages/core/src/workout.ts`: (1) at a work weight of 60 kg or more the line is a three-step ramp, 40% x 8, 60% x 5, 80% x 3, e.g. "Warm up first: 8 reps at 24 kg, then 5 at 36 kg, then 3 at 48 kg. ## 1. Setup and targets  → fixture `targets.json`

**Inputs:** sex, age (18–90), height (cm or ft/in), weight, activity (`sitting|light|feet|physical`), where (`gym|dumbbells|bodyweight`), days (0–7), experience (`new|some|exp`), minutes (30/45/60/75/90), goal (`lose|recomp|maintain|gain`), pace (`gentle|moderate`), pregnancy/breastfeeding (women), 6 health-check answers.

**Calculation (`calcTargets`)**
- BMR: Mifflin-St Jeor `10·kg + 6.25·cm − 5·age + (male ? 5 : −161)`.
- Movement: `BMR × {sitting .15, light .30, feet .45, physical .60}`.
- Training/day: `days × (minutes/60) × 4 × kg / 7` (≈5 METs lifting, net of resting 1).
- TDEE = (BMR + movement + training) / 0.9 (digestion ≈ 10%).
- Goal adjustment: lose gentle −15%, lose moderate −20%, recomp −10%, maintain 0, gain +7%. Pregnant/breastfeeding: never a deficit.
- Deficit capped at 750 kcal; floor 1,500 (men) / 1,200 (women), never above TDEE before rounding. Round to 10.
- Protein: 2.0 g/kg (lose, recomp) else 1.8 g/kg, on a reference weight at BMI 27 when BMI > 30; rounded to 5.
- Fat: max(25% of kcal, 0.6 g/kg). Carbs: the rest.

**Fixture rounding.** The golden fixtures store some values rounded; ports compare after applying the same rounding. Inferred from the data and the prototype, since the generator that wrote them is not in the repo.

`targets.json` (prototype keys `refW` and `weekly` are stored as `refWeight` and `weeklyKg`):
- `tdee`, `bmr`, `movement`, `training`, `digestion`: `calcTargets` returns them unrounded; the fixture stores whole kcal, `Math.round` (the prototype's `fmt`, as the screen shows them).
- `kcal`: rounded to 10 and `protein` to 5 by `calcTargets` itself; `carbs` and `fat` come out whole from `calcTargets`.
- `refWeight`: whole in every current case because every fixture weight is whole; `calcTargets` returns the body weight unchanged when BMI is 30 or below, so ports round it with `Math.round` before comparing.
- `weeklyKg`: 2 decimals, `Math.round(x * 100) / 100` (`toFixed(2)` agrees on every current case). The screen shows 1 decimal; the fixture keeps 2.
- Negative zero is stored as `0` (two current cases produce `-0`); normalise before comparing with `Object.is`.

`formulas.json`: `navyBodyFat` is rounded to 1 decimal (`navyBF` returns 25.2156 and 32.3715; the fixture stores 25.2 and 32.4), although the screen shows a whole percentage. Water, fibre and workout burn come out whole from the prototype.

Other fixtures: `plan.json`, `sessions.json` and `exercises.json` hold no fractional numbers; `foods.json` and `progression.json` hold at most one decimal, as the prototype holds them.

**Floor and rounding (decided on #41).** A floored target is `min(floor, TDEE)`, then rounded to 10. When TDEE is at or above the floor the target is exactly the floor. When TDEE is below the floor the target is TDEE rounded to the nearest 10: up to 5 kcal above TDEE (TDEE 1,195 gives 1,200) or below it, and below the floor itself (TDEE 1,150 gives 1,150). Kept: such users eat at maintenance, and the rounding gap is at most 5 kcal.

**Limits before rounding (decided on #131).** Setup (`validateStep` step 0) checks height (120–230 cm, from cm or ft/in) and weight (30–300 kg) on the values as typed, then saves height rounded to 0.1 cm and weight to 0.1 kg. So 29.96 kg and 119.96 cm are rejected although they would save as 30.0 kg and 120.0 cm. Kept: the values sit at the edge of the range and the user can type the rounded value.

**Health check:** any "yes" or pregnancy → `needsClearance` until the user taps "My doctor has cleared me": sessions are light (one fewer set, no weight increases) and a card explains why.

## 2. Plan engine  → fixtures `plan.json`, `sessions.json`

| Days | Split | Weekdays (Mon=1) |
| --- | --- | --- |
| 0 | No plan | — |
| 2 | Full body A, B | 1, 4 |
| 3 | Full body A, B, C | 1, 3, 5 |
| 4 | Upper A, Lower A, Upper B, Lower B | 1, 2, 4, 5 |
| 5 | Push A, Pull A, Legs A, Upper B, Lower B | 1, 2, 3, 5, 6 |
| 6 or 7 | Push/Pull/Legs A and B | 1–6 |

Session build order (`buildSession`):
1. Template → home mapping (`AWAY` table) if `where` is not gym (day override beats profile).
2. Exclusions and swaps resolve each name (`resolveSession`; swap targets and picks mapped for `where`; replacements, swap targets and picks not already in the session, else the next-best candidate, else a "fewer sets" note, #110, #143; a swap with a running bridge is kept, its old exercise staying as the 2-set bridge; a stored skip still skips with no note); ladder "bridge" exercises appended with 2 sets for 2 weeks.
3. Trim to the exercise cap (30 min → 3, 45 → 4, 60 → 5, 75 → 6, 90 → 7). The first 2 lifts always stay; the extras **rotate** by how many times this template was done (`trimSession`).
4. Focus muscles (`applyFocus`), then the check-in "short session" cut.
5. Sets: 3 default; 2 for `exp=new` in the first 14 days from profile creation; calf raises at least 4; +1 on focus exercises (max 5). Deload: ~60% of sets. Light day: −1 set.
6. Age 60+: append "Single-Leg Balance (seconds)", 2 sets.

Weekly coverage meter: planned (from templates) and done (last 7 days of logged sets). Primary muscle = 1 per set, secondary = 0.5. Under 6 is flagged; ~10 is the target, 12–16 for focus muscles.

**Coverage meter simplifications (decided on #155: kept for M0).** The meter is a weekly guide, so the prototype's shortcuts stay:
- The planned meter (`weeklyCoverage`) counts every exercise of each template at 3 sets (a bridge at 2). It ignores the session-length cap, focus additions, the beginner 2-set fortnight, calf raises at 4, the 60+ balance exercise, and deload or light days, so short sessions are overstated.
- It maps templates for the profile's `where` (`homeWhere()`), not a day's override.
- Untagged exercises count nothing.
- Focus toggling (`focusAction`) checks the whole stored focus list against the limit of 3, while the picker shows its first 3 (`focusList`). The contract caps focus at 3.
- Front shoulders, forearms and lower back are counted but never shown (`COVER_SHOW`) or offered as focus muscles.

Still open (#155): after M0, the planned count may move to the built session's real set counts. That would be a prototype spec change first.

**Missing training days (decided on #72).** `splitFor` treats `days === 0` as no plan but a missing or null `days` as the full 6-day plan, while `calcTargets` treats null as 0 training days. Kept as is: setup makes days (0 to 7) a required answer, so a set-up profile always has it; the case only arises before setup or with damaged data.

**Rotation counting (decided on #73).** `trimSession` counts every stored session entry for the template, whatever its date. Entries are stored only while at least one work set (not warm-up) is done (`saveDay` deletes the entry when sets return to 0), so empty entries never occur. Today's preview is shown only while today has no exercises, so today's own entry never shifts it; a started workout's exercises are fixed when built on Start. Because counting ignores dates, a past day's preview also counts later sessions, and a second session of the same template counts today's entry. Kept as is (and again on #104).

## 3. Weight guidance  → fixture `progression.json`

- Per exercise metadata: type, rep range, step (`EX_META`, `DEFAULT_STEP`). Home dumbbells raise dumbbell ranges to at least 10–20.
- Double progression (`suggestBase`): top of range on every set with no Hard/Fail → +1 step (assisted: −1 step of assistance). Below range twice running, or a failed set → drop ~7.5% (≥ 1 step). Else same weight, +1 rep target.
- Holds: first 14 days on an exercise (unless all sets rated Easy); last session's form = "no".
- Jumps over 10% (5% for age 60+) carry a "go back and add reps" fallback.
- Modifiers (`applyMods`): returning after an exclusion → 55% of old top for 2 weeks; bridge → 85% (assisted: see section 0, #103); deload −10%; re-entry after a break −15% or −30%.
- In-session: Easy → next set +1 step; Couldn't finish → −10%; ticking an empty set uses the placeholder.
- Find-your-weight ramp for first-time loaded exercises: Easy → add a step and another ramp set; Just right → working weight; Hard → one step lighter; Fail → previous ramp weight.
- Stall: best session score (Epley `w·(1+r/30)`; bodyweight = total reps; assisted = `max(r·max(0, bodyweight − assist))`, or `max(r·2 − assist)` with no profile weight) not beating the earlier best by >1% for 3 sessions. 3+ stalled lifts → recovery-week card.
- Personal best: new session score > previous best × 1.005 → toast once a day per lift.

**Personal-best edge cases (decided on #123: kept).**
- A lift whose earlier scores are all 0 never records a best: the check needs a non-zero earlier best.
- Exactly 0.5% better counts as a best, because `100 × 1.005` is `100.49999…` in floating point.
- Bodyweight scores are total reps, so one extra easy set counts as a best.

**Kept on #104.**
- Bodyweight rep targets go up by one rep from last time and are not raised to the bottom of the range (3 reps last time gives a target of 4 on an 8–20 range). Loaded lifts are raised to the bottom of the range.
- The big-jump fallback says "go back to X kg and add reps instead" with plain "kg", without "each" (dumbbells) or "assist" (assisted machines).
- Returning (55% of the old top) and deload (−10%) stack, to about 50% of the old top. This errs light.

## 4. Exclusions, swaps, ladders  → fixture `exercises.json`

- Exclusion scope: exercise, family, movement pattern, or joint; duration: today, 2 weeks, 4 weeks, permanent. Re-check card when a timed rule ends.
- Replacement scoring (`candidates`): shared primary muscles ×10, shared secondary ×2, same pattern +6, joint-stress and difficulty penalties, history +2, equipment filter by `where`.
- Ladders (`LADDERS`): step-up card after ≥4 sessions at the top of the range with good ratings and solid form; 2-week bridge; step-down after two bad sessions; "stay" re-asks after 6 weeks.
- Custom exercises: Claude suggests tags (pattern, equipment, muscles, joints); user confirms on a body map; stored per user. A typed name that matches a known exercise in any letter case is that exercise, not a new custom one (differs from the prototype's exact-case check, #665).

## 5. Food  → fixture `foods.json`

- All values per serving; carbs include fibre. Grams entry works for foods whose unit is in grams.
- Grams logging (decided on #97: kept) reads the grams from the serving label, including a bracketed ingredient or dry weight (`unitGrams`): "1 medium (30 g atta)" is 30 g, rice 50 g raw, dal 35 g, rajma/chole 40 g dry. So typed grams mean that weight, and 60 g of cooked rice logs 1.2 servings. The app says so in the hint under the grams input ("Grams are the weight in the brackets on the serving (the dry or ingredient weight, such as "50 g raw"), not the cooked weight.") and shows each food's own label on its row, such as "1 cup (50 g raw)". No per-food toast: the "Added Rice, cooked (60 g)" toast stays as the prototype has it. No content change.
- Search matches name or alias (`ALIAS`: chawal, anda, dahi, daru…).
- Fibre target: max(25 g, 15 g per 1,000 kcal of today's target). Fruit & veg servings out of 5. Added sugar shown when ≥10 g.
- Meal ideas (`combos`): protein shortfall weighted 3× calorie error; caps per food (`MAXQ`), minimum portions (`MINQ`); age 60+ ≥25 g protein per main meal; diet filter any/egg/veg; fasting-day pool.
- Day complete: user tick, or for older days ≥3 meals and ≥75% of target. Only complete days feed the real-burn estimate.
- Recipes: raw ingredients per 100 g (`RAW`, `RAW_FIB`), cooked yield by katoris (150 g) or pot weight.
- Kitchen tests: pot weights → cooked weight; per 100 g and per serving; "use for my logging" writes a personal food.
- Logging and saving checks (#150): grams that round to 0 servings are not logged; a custom food, recipe or kitchen test with a trimmed name over 200 characters, or a negative amount or value (a custom-food quantity at or below 0), is not saved.

**Kept on #151.**
- Fibre, added sugar and fruit and veg are looked up by the logged item's name, not a food id, so a custom log named like a shared food gets the shared food's values. For fibre and added sugar a shared food's entry wins over a user food of the same name (`fibOf`); for fruit and veg the shared value wins only when it is not 0, so a shared 0 lets the user food's value count (`produceOf`). Revisiting `food_id` lookups when the sync client lands is tracked in #648.
- Search matches a food's aliases as one string joined with spaces, so a query can span two aliases ("fulka rotli" finds Roti / chapati).
- `unitGrams` reads whole numbers only: a decimal loses its whole part ("1.5 g" reads 5). No content label has a decimal gram weight.
- The added-sugar line checks the unrounded total, so 9.6 g is hidden although it would show as 10 g.
- "≥3 meals" for a complete day counts logged items, not meal slots: three items in one meal count as three.
- Cola's added sugar (35 g for "Cola (330 ml)") is in the eat-out table only. The eat-out dishes carry fibre and added sugar from the prototype's `FIB` (#858), and the Food totals count them by logged name, as the prototype's `fibOf` does (#866), so a logged Cola counts 35 g.

## 6. Progress and coaching  → fixture `formulas.json`

- Real burn: average intake on complete days − (weight trend slope × 7,700 kcal/kg); needs ≥10 complete days in 14 and ≥6 weigh-ins in 21; smoothed 60/40 with last week. Suggest a calorie change only if the new target differs by ≥100 kcal.
- Rapid loss: weekly average down >1% for 2 weeks (or 1 week plus 2+ stalls) → suggest +150 kcal.
- Navy body fat, water target (33 ml/kg + 600 on training days), workout burn (session time × 5 METs; extra over resting at 4), steps target (recent average + 1,000, 5k–12k).
- Habits: on-track weeks = consecutive weeks with ≥ (plan days − 1, min 2) sessions.
