# Reading content bundles in screens

Server copies of the `content/*.json` bundles are fetched and stored by `refresh.ts`, chosen once at app start by `loadContent` (called from the database `onInit` in `app/_layout.tsx`) and applied on the NEXT launch. No hot-swap.

## Why readers are lazy

`SQLiteProvider` renders its children (the router and every screen) only after `onInit` has finished, so `loadContent` has always run before any screen code. What broke the first design was module-level constants such as `export const catalogFoods = foods.foods`, evaluated when the module is imported, which can be before the database init. So: never build anything from a content import at module level. Build it in a getter.

## The pattern (copy `src/food/catalog.ts`)

1. Keep the static JSON import. It is the synchronous baseline and the fallback.
2. Write ONE pure validator `(v: unknown) => v is Raw` for the whole bundle, as the contract (`openapi.yaml`) and `content/` spec require, run once per bundle: every row, every required key, its type and its contract bounds (finite numbers, minimums such as `>= 0` and `exclusiveMinimum: 0`, uuid ids, `maxLength`s, enums such as `FoodSource.code`, and URLs allowed only as null or `https://`; use the shared `isFoodSource` for any bundle with a `source`), plus a generous upper bound for values the contract leaves open (check the shipped data's real ranges and leave headroom). Reject empty lists where an empty bundle would leave a screen useless. It must never throw (a throw counts as a rejection). Do not write a second, narrower validator for another reader: that lets two screens disagree about one stored copy.
3. Export the single decision: `export const chosenFoods = contentReader('foods', shippedImport, isFoods);`. It returns the stored copy chosen at app start only if the whole bundle validates, else the shipped import, and runs once until the next `loadContent`. Every reader of that bundle (catalog, About sources, and so on) derives from this one getter, so a stored copy is wholly used or wholly rejected. Derive values with `perLoad(() => chosenFoods().foods)`; `perLoad` computes at first call after each `loadContent` and is memoised.
4. If screens look rows up by name (past-day totals, core meal rules), the validator must also require every name in the shipped copy (additions and value edits allowed; removals and renames reject the copy). Foods does this. Meal planning does it per section: a name in the shipped roles, grocery, max or min list must stay in that same section of a stored copy (being in another section does not count), every name the copy uses must be a food in the chosen foods bundle (eat-out dishes do not count), and roles and grocery foods must be unique (trim, lowercase).
   Raw ingredients and recipes (`src/recipes/content.ts`): the validator is as strict as `tools/validate/recipes.mjs` (it skips only that tool's unknown-field check, so a newer server may add fields). The ingredient picker offers only the SHIPPED raw names, and a recipe may only use shipped names, so for v1 the server cannot add a recipe that uses a new raw ingredient (intended). Server-added raw rows are validated but not offered, so a saved recipe or kitchen test never names an ingredient a later copy drops (core skips a missing ingredient and the numbers would change). A stored-ingredient snapshot would lift this limit (follow-up issue).
5. Replace each use of the old constant with a call to the getter, inside the function or component (never at module level).
6. Tests (see `__tests__/content-readers-foods.test.ts`): shipped copy when nothing is stored; a valid newer copy is used only after `loadContent` (assert the same reference and a validator spy count, so the test fails without the memo); one rejection case per checked key and bound (negative, huge, zero, non-uuid, empty, 5000 characters); a validator that throws; every reader of the bundle agrees on accept and reject.

A bundle `name` is the file name without `.json` (it must exist in `bundled.json`). `loadContent` already drops copies whose `schema_version` this build does not support.

A bundle that another area still reads from the shipped import is read from the shipped import by every reader until all of them move together. (raw-ingredients and recipes moved together: `src/recipes/content.ts`.)

## Exercises (`src/workout/catalog.ts`)

The exercises bundle is read through `chosenExercises` / `getCatalog`. A stored copy is rejected whole unless it keeps what the shipped copy fixes: every shipped exercise with its `meta.type` and `tags.equipment`, the shipped order of tags, every away entry, and every shipped ladder pinned BY POSITION (each shipped step keeps its names first and in order; steps, names after them and new ladders may be appended). So prepending an easier step to a shipped ladder, or reordering ladders or steps, rejects the copy. This is intended for v1 (conservative: a ladder position is what stored step-up and step-down history means); relax it only with a migration plan.

## Exercise figures (`src/workout/figures.ts`, `ExerciseFigure.tsx`)

`chosenFigures` reads `exercise-images` (inline SVG per exercise). Its validator is an allowlist: each frame is tokenised and refused unless it is one `svg` root (xmlns and a matching viewBox only) holding only `g line circle ellipse rect path polyline polygon`, double-quoted allowlisted attributes, no `:` or `url` in values, and `fill`/`stroke` set to `none`, `currentColor` or `var(--fig-body|arm|hl|eq|bg)`. One bad frame or field refuses the whole stored copy (the shipped one stays). The SVG is only ever given to react-native-svg (`SvgXml`) after the `--fig-*` variables and `currentColor` are replaced by palette colours; never inject it into the DOM. Keep this list in step with `tools/validate/exercise-images.mjs`.
